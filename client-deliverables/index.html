Data Processing Logic

How each metric is computed — the implementation guide for building this in the PM tool

Every metric below is derived from the PM tool's own per-ticket status-change history — a log of (previous_status, new_status, changed_on, assignee) rows — except automation and test-execution counts, which come from TestRail. Status vocabulary: QC = {QC Testing, QC Testing in Progress, QC Testing Hold}, QC Review Fail, BIS Testing, CLOSED = {Closed, Moved to Live}.

1 · Average QC cycle time (QC → BIS)

Per ticket, the calendar time from the first entry into any QC status to the first time it reaches BIS Testing. The tile shows the mean over tickets in the period.

qc_to_bis_days(ticket) = first( change where new_status == "BIS Testing" ).changed_on − first( change where new_status ∈ QC ).changed_on Avg QC cycle time = mean( qc_to_bis_days ) over period tickets
2 · Average QC Testing Time (First Pass)

Total days a ticket spends across the three QC statuses, counted only for its first time in QA testing (excludes Approved-for-Live, the BIS approval wait, and any rework).

qc_wait(ticket) = Σ days in {QC Testing, QC Testing in Progress, QC Testing Hold} A QC entry is FIRST-TIME when: new_status ∈ QC AND previous_status ∉ QC AND prior_qc_entries(ticket) == 0 AND previous_status ∉ REWORK where REWORK = {QC Review Fail, Code Review Failed, Tested - Awaiting Fixes, BIS Testing} Avg first-time QC wait = mean( qc_wait ) over first-time tickets
3 · Retests (Tracked Separately)

When a ticket fails a QC review (QC Review Fail) it goes back for fixes, then returns to QC as a retest. Retests are tracked separately so rework never inflates the first-pass testing time. Retest count per ticket = number of QC review failures.

A QC entry is a RETEST when: new_status ∈ QC AND previous_status ∉ QC AND ( prior_qc_entries(ticket) > 0 OR previous_status ∈ REWORK ) Retest count = number of retest entries in the period Avg retest wait = mean QC dwell measured over retest legs only
4 · Average Moved-to-Live → Closed wait

Calendar days from the ticket reaching Moved to Live until it is finally Closed.

mtl_to_closed(ticket) = closed_on − first(new_status == "Moved to Live").changed_on Avg = mean( mtl_to_closed ) over tickets closed in period
5 · Spike detection & cause attribution

Run over the monthly trend series. A point is a negative spike (worse) when it breaks either threshold. The cause is the driver whose standardised increase over the baseline is largest; the offending-ticket list is the worst individual contributors in that month.

For metric M over the trend: μ, σ = mean & stdev of the trailing 6 points (excluding current) SPIKE if M_current > μ + 2σ OR M_current ≥ 1.5 × M_previous Cause drivers (ranked by standardised delta vs baseline): • longer testing time → rise in avg QC days at flat volume • more bugs reported → rise in bug count • more retest cycles → rise in retest re-entries / avg cycles Offending tickets = tickets in the spike month whose own metric exceeds (per-ticket μ + 2σ), sorted desc, top 10.
6 · Team-member velocity profile

Velocity is shown as a full work profile, not a single number — so a member handling fewer but harder tickets is not read as low output. Each figure is broken down by ticket complexity (High / Medium / Low). The single velocity number (complexity points per week) is used only for the Volume vs Velocity chart.

Per member, per period: attended = tickets handled (delivered + in-progress + awaiting) handed_to_bis = tickets moved to BIS Testing closed = tickets closed (Moved to Live) in period tests_executed = TestRail executions attributed to the member bugs_reported = bugs the member raised retested = retest re-entries on the member's tickets complexity mix = count of High / Medium / Low among those tickets Complexity multiplier: High = 1.9, Medium = 1.0, Low = 0.7 Composite velocity = Σ( complexity_multiplier over closed tickets ) / weeks_in_period
7 · Automation utilisation (TestRail)

From TestRail: each case has an automation status; each execution row records whether an automated case ran. Module is resolved from the TestRail section via the module-ownership mapping.

coverage% = automated_cases / automatable_cases × 100 utilisation% = automated_executions / total_executions × 100 reuse_ratio = automated_executions / automated_cases time_saved_h = automated_executions × manual_minutes_per_case / 60 (all of the above also computed per module)
